# Migration Safety

Migrations are the one part of a codebase where a bug destroys data instead
of just returning it wrong. Hand-written migrations in fast-built projects
repeatedly ship missing columns, wrong types, destructive table swaps, and
empty rollbacks. This skill covers both **authoring** and **reviewing**.

## Non-negotiable rules

1. **Never hand-write a migration from scratch.** Always
   `alembic revision --autogenerate`, then review and edit the output.
   Hand-written migrations reliably miss columns the model has (defaults,
   timestamps, nullable flags) and drift from reality — a defect class that
   recurs until autogenerate becomes the rule.
2. **An empty `downgrade()` is a blocking finding.** `def downgrade(): pass`
   means "this deployment cannot be rolled back." If a real downgrade is
   truly impossible (data destroyed on upgrade), the function must
   `raise NotImplementedError("irreversible: <why>")` so a rollback attempt
   fails loudly instead of silently succeeding at nothing.
3. **A rename is not drop + add.** Autogenerate cannot detect renames — it
   emits `drop_column` + `add_column`, which destroys the data in that
   column. Every autogenerated drop must be interrogated: is this actually a
   rename? Use `op.alter_column(..., new_column_name=...)` /
   `op.rename_table(...)`.
4. **Dropping a table that contains data requires a data-preservation plan
   in the migration itself** — migrate the rows to the new structure, or
   explicitly document (in the migration docstring) that destruction is
   intended and why. "The new schema replaces it" is not a plan; it's how
   production data disappears during a refactor.
5. **`NOT NULL` on an existing table needs a path for existing rows:** add
   with `server_default`, or add nullable → backfill → alter to non-null.
   Otherwise the migration fails on any table that has data — meaning it
   passes in dev (empty DB) and fails in production.
6. **Schema migrations and data migrations stay separate.** A data backfill
   inside a schema migration can't be retried independently and often can't
   be reversed. Separate revisions, data migration clearly named.
7. **One head.** `alembic heads` must return exactly one revision. Two heads
   mean parallel branches that will fail on deploy.

## Authoring workflow

1. **Pre-flight:**
   ```bash
   alembic current && alembic heads      # single head, current == head
   alembic revision --autogenerate -m "check" && cat <generated>  # drift check
   ```
   If the drift-check revision is non-empty, the models and DB already
   disagree — stop and resolve that first (someone hand-edited one of them).
   Delete the check revision afterward.
2. **Make the model change**, then `alembic revision --autogenerate -m
   "<imperative description>"`.
3. **Review the generated file line by line** against the rules above.
   Autogenerate is a draft, not an answer: it misses renames, server
   defaults, and some type changes; verify enum changes and
   `ARRAY`/`UUID`-style dialect types explicitly.
4. **Write the real `downgrade()`** and check it mirrors upgrade in reverse
   order (constraints off before columns drop, etc.).
5. **Dry-run the round trip on a scratch database with realistic data** —
   not an empty one; rules 4 and 5 only bite when rows exist:
   ```bash
   alembic upgrade head
   alembic downgrade -1
   alembic upgrade head
   ```
   Verify row counts on affected tables before and after.
6. **Post-flight drift check:** run autogenerate again — it must produce an
   **empty** revision. Non-empty output means the migration doesn't fully
   implement the model change (the classic missing-column bug). Delete the
   check revision.

## Review checklist (for someone else's migration)

- [ ] Produced by autogenerate (structure/comment style shows it) or the
      author explains why not
- [ ] `downgrade()` is real, or raises with a documented reason
- [ ] Every `drop_column`/`drop_table` interrogated: rename? data preserved?
      destruction explicitly intended and documented?
- [ ] New `NOT NULL` columns on existing tables have `server_default` or a
      backfill step
- [ ] No data manipulation mixed into a schema migration
- [ ] `alembic heads` → one head; revision chain is linear
- [ ] Revision message says what it does; naming consistent with the chain
      (misnamed revisions like an "001_" prefix appearing mid-chain make the
      history unreadable)
- [ ] Round-trip dry run reported by the author, with row counts, on a
      non-empty database
- [ ] Migration runs inside the project's container against the project's
      real database engine (never a different dialect)

## Diagnosing model/schema drift

When the app 500s with column-mismatch errors or autogenerate emits
surprising diffs:

```bash
alembic current                          # what the DB thinks it's at
alembic history --verbose | head -30     # what the chain thinks exists
alembic revision --autogenerate -m "drift-probe"   # the actual delta
```

The probe revision's content *is* the drift report. Fix by writing a
corrective migration (autogenerated, reviewed as above) — never by
hand-editing the database, and never by editing an already-applied migration
file (its hash of record has shipped; applied history is append-only).

## Exit criteria

- Round trip (`upgrade → downgrade → upgrade`) clean on realistic data,
  row counts verified
- Post-flight autogenerate diff is empty
- Single head; real or explicitly-raising downgrade
- Review checklist passes
