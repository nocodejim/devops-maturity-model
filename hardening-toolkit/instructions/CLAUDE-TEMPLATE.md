## Pre-Commit Protocol — every commit, no exceptions

1. **Verify in the real environment.** Build success, exit code 0, and HTTP 200
   are not verification. Frontend changes: exercise the flow in a browser and
   check the console. Backend changes: call the endpoint and assert on the
   response body. (See the `verify-real-environment` skill for the full ladder.)
2. **Run the gates:** {{GATE_COMMANDS — e.g. backend lint + tests, frontend `tsc`/build + tests}}.
   A frontend commit without a passing type-check is not a commit.
3. **Update the record:** if anything went wrong or you learned something,
   add a `docs/lessons-learned.md` entry (template below). Update the progress
   tracker for completed milestones.

**Commit message format:**

```
<type>: <subject>

<body: what changed and why>
```

Types: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `ci`.

## Critical Rules — NON-NEGOTIABLE

- **NO TIME ESTIMATES.** Never put durations in plans, roadmaps, or docs
  ("Week 1-2", "this will take about..."). List phases and steps; the humans
  decide timing.
- **Docker safety.** Never run commands that affect the host or other
  projects: no `docker system prune`, no `docker volume/network prune`, no
  `--all`/`-a` flags outside this project. Project-scoped `docker compose`
  commands only.
- **Never mark a feature complete without real-environment verification**
  (browser for frontend, functional API calls for backend).
- **Never hand-write a database migration from scratch.** Autogenerate, then
  review. Empty `downgrade()` functions are a blocking review finding.
  (See the `migration-safety` skill.)
- **No secrets in code — including defaults.** No secret-shaped default values
  in config classes, no credentials in compose/manifest files, no seeded admin
  users outside an explicit dev-only flag. A secret committed once is
  compromised: rotate it. (See the `secrets-config-hygiene` skill.)
- **Structured logging only.** No `print()` in backend app code; no
  `console.log` of credentials, tokens, or response bodies — ever, in any
  environment. Use the project logger; gate verbose output to dev.

## Definition of Done — review checklist

A change is done when all of these hold:

- [ ] Verified in the real environment, with observed evidence (actual output,
      not "should work") included in the completion report
- [ ] Tests exist for the change; every bug fix ships with a regression test
- [ ] No new broad/silent `except` blocks; errors are logged with context or
      propagated — never swallowed into a default value
- [ ] No new secrets, secret-shaped defaults, or credential logging
- [ ] Schema changes: migration autogenerated + reviewed, `downgrade()` real,
      dry-run `upgrade → downgrade → upgrade` passed
- [ ] No dead code left behind (commented-out routers, stub API clients,
      orphaned modules) — delete it; git remembers
- [ ] Lint, format, and type-check gates pass
- [ ] Docs updated where behavior changed
